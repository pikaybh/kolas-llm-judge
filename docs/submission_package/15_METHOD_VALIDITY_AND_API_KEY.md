## 1. 목적 적합성 및 공인시험 요건과의 연결

비교행렬 방법은 기준 위험요인의 문장을 기계적으로 일치시키는 것이 아니라 **시공작업의 위험원, 사건 발생 메커니즘, 작업·노출 맥락 및 피해 메커니즘**에 근거해 AI 출력의 식별 기능을 측정한다. 건설 위험성평가에서 동일한 위험은 서로 다른 문장으로 기술될 수 있으므로, 단순 문자열 일치법보다 시험대상 기능에 직접 대응하는 장점이 있다. 이러한 논증은 **시험방법 채택의 기술적 근거**이며, 외부 검증·승인 완료를 의미하지 않는다.

한국인공지능검증원 2026-09-15 및 2026-10-13 회신의 요청사항과 방법상 조치:

| 시험기관 요청사항 | 본 방법의 대응 및 확인 증거 |
|---|---|
| 유효성 / 목적 적합성 | GT-출력간 기계적 단어일치가 아닌 위험 메커니즘·맥락·피해의 동일성 판단. 독립 안전전문가와의 교차검증·오류분석 계획을 포함 |
| 객관성 | Boolean rubric을 미리 고정하고, 각 쌍의 세 판단값과 최종 결론을 분리 기록 |
| 재현성 | 모델·프롬프트·설정·데이터·평가기 소스 SHA-256 동결, 고정 시나리오, 동일 조건 반복 |
| 추적성 | case_id → reference_id → generated_id → 판정결과 → run_id → 시각·버전·해시 연결 |
| GT 적정성 | 기존 연구실이 검증한 GT를 유지, 출처·ID·학습/시험 중복 여부 확인표 첨부 |
| 위험요인 원자화 | 복합 문장·중복 위험요인 처리 지침 및 원출력/정규화 결과 보존 |
| Judge 적격성 | 적격성 통제집합 + 독립적인 전문가 기준 판정값 대조, 불일치 adjudication |
| 반복시험 | 모든 반복에서 새 SUT 결과 생성, 반복별 matrix/통계/실패원인 분리 기록 |
| 오류 처리 | SUT 미완료 / evaluator 실패 / infrastructure 실패 구분 및 누락분모 공개 |
| 조건 사전 확정 | 기준식, 측정명, 분모, 반복수, 합격선 등 시험기관 승인 뒤 freeze |

관련 기준: KS Q ISO/IEC 17025:2017 제7.2(방법 선정·검증), 제7.5(기술기록), 제7.7(결과의 유효성 보장). **KOLAS 공인시험방법으로서의 최종 수용 여부는 시험기관의 심사·승인사항이다.**

## 2. 수학적 측정모형

시나리오 `s`의 GT 위험요인 집합을 `R_s={r_s1,…,r_sn}`, SEEXR 생성 위험요인 집합을 `G_s={g_s1,…,g_sm}`이라 한다. 모든 `(r_si,g_sj)` 조합에 대해 Judge가 다음을 독립적으로 이진 판정한다.

- `H_sij ∈ {0,1}`: 동일한 위험 발생 메커니즘(원인-사건-피해)인지
- `C_sij ∈ {0,1}`: 작업/설비/노출 맥락이 동일하거나 모순 없이 양립 가능한지
- `A_sij ∈ {0,1}`: 사고 또는 피해 메커니즘이 직접적으로 양립 가능한지

기본 엄격 의미판정 행렬:

`M_strict[s,i,j] = H_sij ∧ C_sij`

기존 제품 지표와의 연속성을 위한 넓은 위험요인 식별 판정 행렬:

`M_broad[s,i,j] = (H_sij ∧ C_sij) ∨ A_sij`

`M`은 `n_s × m_s` 이진 행렬이다. 기준 위험요인 `r_si`의 식별 여부:

`I_s,i(M) = 1 - ∏_(j=1)^m_s (1 - M[s,i,j]) = max_j M[s,i,j]`

생성 위험요인 수 `m_s=0`이면 `I_s,i=0`. 한 기준 위험요인과 일치하는 생성 결과가 여러 건이더라도 **분자는 최대 한 건만 인정**한다. 한 생성 위험요인이 두 개 이상의 서로 다른 GT 메커니즘을 실제로 모두 포함한 경우, 각각을 **독립적으로 만족한다고 Judge가 판단한 경우에만** 각 reference를 인정한다.

평가 완료된 비교행렬을 갖는 기준 위험요인 집합을 `E`, 전체 시험의 기준 위험요인 집합을 `T`라 하면:

`HIA_evaluable = 100 × (Σ_(r∈E) I_r(M_broad))/|E|`

`StrictSemanticRecall = 100 × (Σ_(r∈E) I_r(M_strict))/|E|`

`HIA_end_to_end = 100 × (Σ_(r∈T) 1[r∈E] I_r(M_broad))/|T|`

`CompletionRate = 100 × (SUT 완료 시나리오 수)/(전체 시나리오 수)`

**분모 |E|와 |T|는 반드시 같은 표나 그래프에 병기한다.** `HIA_evaluable`은 평가가능 표본의 조건부 식별률이고, `HIA_end_to_end`는 미완료를 식별 실패로 처리한 전체 입력 기준 지표이다. 평가기 자체 장애는 별도 taxonomy에 따라 재시험하거나 판정 보류하며 조용히 제외하지 않는다.

보조 1:1 matching은 strict 판정 쌍에 대해 최대 cardinality matching을 수행하여 생성 항목과 GT의 독립적 대응 가능 건수를 측정한다. **주지표의 분자 계산에는 이 1:1 제약을 적용하지 않는다.**

## 3. 넓은 판정의 공학적 의미와 제한

건설 현장에서 하나의 위험은 장비·작업 내용에 따라 다른 문장과 사고 시나리오로 표현된다. `H∧C`는 위험 발생조건을 직접 재현한 강한 동일성 기준이며, `A`는 작업·피해 위험을 **기능적으로 식별했는지**를 관찰하는 추가 축이다. 넓은 KPI는 GT와 표현이 다른 출력 중 안전관리 목적상 동등한 사고/피해 메커니즘의 식별을 포착하도록 설계됐다.

그러나 `A=1`만으로 인정하면 단순히 '추락', '끼임' 같은 **광범위한 사고분류가 동일한 것만으로 허위 양성**이 발생할 수 있다. 현재 Rubric 문구는 '사고유형/피해 메커니즘이 동일·양립'으로 정의되어 있어 이 위험을 해소했다고 볼 수 없다. 따라서 넓은 판정을 공식 Primary로 채택하려면 **A-only 양성 사례를 별도로 추출하여** 독립 전문가에게 위험원·사건·피해 연결의 기술적 등가성을 검증받고, 부적절한 사고유형만 일치한 사례의 허위 양성률을 보고해야 한다. 새 기준을 사후 적용하면 기존 95.67%와 직접 비교할 수 없으므로 버전·재시험이 필요하다.

공식 frozen runtime 현재 설정은 `StrictSemanticRecall`을 Primary, 넓은 `HIA_evaluable`을 supplementary로 둔다. 넓은 HIA의 Primary 채택과 95% 적합 판정은 **시험기관과 합의한 후** 별도 기록으로 승인·동결하며, 승인 전 공식 성적을 단정하지 않는다.

## 5. Judge 측정시스템 유효성 확인 절차

1. 판단 기준 사전 등록: 모델 식별자·버전, system/developer/user 프롬프트, rubric, structured schema, sampling/reasoning 설정, 동시성/타임아웃, 결측 처리 정책, 모든 파일 해시
2. 대조 기준: 개발 과정에 관여하지 않은 건설안전 전문가 **2인 이상**의 독립 판정 + 불일치 합의판정을 독립 표본에 생성(시험기관 합의 표본추출). 연구실 GT가 이미 검증됐다는 사실과 **Judge pair 판정의 검증**은 구분
3. Binary 판정 평가: 전문가 합의값에 대한 각 판단축별 TP/FP/FN/TN, sensitivity=TP/(TP+FN), specificity=TN/(TN+FP), PPV=TP/(TP+FP), 전문가 간 Cohen's κ 및 Judge-전문가 κ 산출. 분모 0인 값은 N/A로 명시
4. 중요 오분류: `A=1 ∧ ¬(H∧C)` 판정(넓은 KPI에서 추가로 인정되는 쌍)의 오인정 사례를 별도 분석
5. 반복성: 독립적인 SUT 재실행 최소 2회 후보, Judge 반복 판정 일치율과 SUT 최종 식별률 변동을 별도 집계. 시나리오·Judge 설정은 반복 간 동일, 출력은 새로 생성
6. 오류 처리: 누락 matrix, 파싱 실패, 서비스 오류, Judge 인프라 장애를 구분하고 오류 로그·재시도 횟수·제외 사유를 보존. 실패가 반복될수록 점수가 높아지는 분모 편향을 별도 보고
7. 보고 불확실성: 단순 비율의 Wilson 95% 신뢰구간과 반복간 범위를 계산하되, 이는 **표본·반복 변동의 참고치**이며 공인시험 불확도 평가의 대체값이라고 단정하지 않음

기준판정값의 작성·검토자 및 Judge 대조 성능은 아직 본 문서만으로 입증되지 않으며, 완료 전에는 '검증 완료'로 표시하지 않는다.

## 6. 시험기관용 API Key 인증 — 개정 계약

통신: HTTPS `https://api.seexr.dev/api`(현재 official-runtime-v1에 frozen된 개발시험 대상); Blue production `https://api.seexr.co.kr/api`는 API 키 인증 변경의 Green 검증과 Blue 배포, 대상 릴리스·시험조건 재동결 후 사용 가능. URL을 혼용하거나 Green 키를 Blue에 제출하지 않는다.

SEEXR 발급 API Key: `SEEXR_API_KEY`; HTTP 헤더 `x-api-key: sk-...`. OpenAI Judge용 `OPENAI_API_KEY`는 독립 credential. JWT `SEEXR_API_TOKEN`은 이전 시험용 단기 bearer이고 API Key와 다르다.

- 전용 active 일반 사용자 계정으로 API Key 발급; 권한을 지정하는 경우 `risk-assessment:run` 포함
- 경로 제한: `GET /agents`, `GET /instructions/me`, `GET /users/me/plan`, `POST /chat/sessions`, `POST /agents/risk-assessment/runs`, `GET /agents/runs/{run_id}/events`
- SSE run 소유권 및 AI token allowance 검증은 기존 서버 검사를 그대로 적용
- 토큰 원문은 한 번만 전달; 실제 키는 환경변수/보안채널로만 제공. 응답·로그·보고서·스크린샷에 삽입 금지
- 키 철회/만료/사용자 정지는 즉시 인증 실패; 잘못된 키가 주어지면 JWT·비밀번호로 자동 우회하지 않음
- 각 요청은 HTTPS API와 서버측 추적기록으로 연결; source SHA, 시각·시나리오·run_id·출력·판정·해시 저장

하네스 설정 예시 (키 문자열은 보고서에 기입 금지):

```dotenv
SEEXR_API_KEY=<secure-delivery>
OPENAI_API_KEY=<secure-delivery>
# frozen runtime이 가리키는 환경과 키 발급 환경이 일치해야 함
```

점검 순서: `doctor --official` → 제한적 `doctor --official --live`(read-only connectivity) → 유료 실행이 발생하는 pilot/full은 시험기관 승인·비용 합의 후 진행. 구체적인 명령은 `README.md`, `docs/submission_package/10_REPRODUCIBILITY_GUIDE.md`, `11_API_ACCESS_GUIDE.md`의 CLI 도움말과 대조한다.
